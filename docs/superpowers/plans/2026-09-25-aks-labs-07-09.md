## Review Focus

1. Same-named Services and identical Pod labels in different namespaces/clusters must never select a foreign backend; short DNS names resolve relative to the client Pod. Tasks 1, 2 and 7 test this.
2. A ready endpoint on a numeric target port does not prove the Python process listens there; changing containerPort alone cannot repair a different captured listener. Tasks 1, 2, 5 and 6 test this.

## Exam grounding and teaching boundaries

The current [AI-200 study guide](https://learn.microsoft.com/en-us/credentials/certifications/resources/study-guides/ai-200) names AKS manifest management and diagnosis using logs, events and end-to-end connectivity. See [Kubernetes Services](https://kubernetes.io/docs/concepts/services-networking/service/). Normal Service DNS names resolve to the Service address; short names use the requesting Pod's namespace. See [DNS for Services and Pods](https://kubernetes.io/docs/concepts/services-networking/dns-pod-service/). EndpointSlices expose backend addresses, ports and readiness conditions. See [EndpointSlices](https://kubernetes.io/docs/concepts/services-networking/endpoint-slices/). Checked 2026-09-25.

The addresses, immediate LoadBalancer provisioning, single-stack IPv4, compressed reconciliation and deterministic backend selection below are explicit trainer choices. No real load balancer, DNS cache, TCP stack, retry policy or packet capture is emulated. A modeled connection failure has a reason and no HTTP status; do not invent HTTP 503 as a Kubernetes network response. Application-generated dependency failures retain the status defined by plan B.

## Extension contract

### State and derived resources

For connectivity-enabled Labs only, each ClusterState gains:

```js
connectivity: {
  version: 1,
  nextServiceAddress: 1,
  nextPodAddress: 1,
  nextExternalAddress: 10,
  diagnosticPodUids: [],
  applicationLogs: [], // max 200; redacted, ordered by run.nextSequence
  incident: null       // Lab 8 only; schema defined in Task 6
}
```

Service addresses are allocated from 10.96.0.1-10.96.15.254; Pod addresses from 10.244.0.1-10.244.15.254, skipping .0/.255. External addresses use the documentation-only range 192.0.2.10-192.0.2.254. Counters advance on resource creation only, addresses are never reused in one run, and exhaustion gives an explicit simulator-limit diagnostic without partial creation. Allocation is per cluster; the cluster identity always participates in resolution. No collision search, wall clock or randomness. Store Service spec.clusterIP, Pod status.podIP and LoadBalancer status.loadBalancer.ingress[0].ip as generated fields. Authors cannot supply them in YAML. Reapplying a manifest preserves generated values and UIDs.

This batch permits creating/deleting ClusterIP and LoadBalancer Services, retaining the existing one-TCP-port schema; reject in-place type changes as unsupported by this trainer. Later support can widen that subset. Services require nonempty selectors. Headless, ExternalName, selectorless Services, NodePort authoring, externalTrafficPolicy and publishNotReadyAddresses remain explicitly unsupported. Default omitted targetPort to port and omitted type to ClusterIP. Named target ports resolve independently against each selected Pod's container ports; numeric target ports need not appear in containerPort declarations.

Derive discovery.k8s.io/v1 EndpointSlice resources in ClusterState.resources. Each has a deterministic name based on Service UID and resolved backend port, ownerReferences to the Service, label kubernetes.io/service-name, addressType IPv4, ports and endpoints with targetRef to a Pod and conditions.ready. Group by resolved port; use one empty slice when no target resolves. Preserve UID/resourceVersion for unchanged content. Pods without an assigned IP do not contribute addresses. Selected Pods with an IP and Ready=false appear as unready endpoints; routing excludes them. A numeric targetPort such as 8081 still produces endpoints even when the application listens on 8080. A named port missing from a selected Pod yields no backend for that Pod and a trainer inspection explanation; do not invent a Kubernetes Event.

The supplied diagnostic Pod is a seeded, Running fixture in namespace diagnostics, with an inspectable fixed image descriptor and label app=diagnostics. Its UID is listed in diagnosticPodUids. It is not selected by assistant Services and has no assistant AppSpec. General Pod YAML creation/exec is outside this increment. Validate the seed against a dedicated diagnostic fixture schema; a learner cannot acquire diagnostic privileges by copying its name or label. Deleting it is unsupported with an explanatory message. Normal managed-Pod deletion remains supported.

On older Labs, absence of connectivity is valid; do not migrate their runs into this richer model automatically. Connectivity-enabled saves must contain a valid extension and owned, unique addresses/UID references. Reject corrupt or forged logs/slices through the existing recover/export/restart path. Derived slices are recomputed on mutations, not silently repaired when loading corrupt saves. Read commands and no-op apply allocate nothing and leave evidence current.

### Resolution and routing algorithm

1. Resolve and validate the origin from current run state. Internal probes require a live supplied diagnostic Pod. External probes carry no caller-selected Pod. Targets belong to the origin cluster.
2. Internal DNS accepts service, service.namespace, service.namespace.svc, and service.namespace.svc.cluster.local with an optional trailing dot. Normalize DNS case; do not make Kubernetes object names case-insensitive. A short name searches only the client namespace. No localhost, IP-as-DNS query, arbitrary suffix, SRV, Pod DNS or external lookup through this Service resolver.
3. Internal HTTP can target those names or a current ClusterIP. External HTTP must target a currently allocated LoadBalancer external IP. An internal-only address/name from an external probe fails with INTERNAL_ADDRESS; an unknown address fails with UNKNOWN_ADDRESS. HTTP only; HTTPS/TLS is visibly unsupported.
4. Match the Service's public port, then resolve selected same-namespace Pods and eligible endpoints. Failure reasons distinguish DNS_NOT_FOUND, SERVICE_PORT, NO_READY_ENDPOINTS, NAMED_PORT_UNRESOLVED and CONNECTION_REFUSED. A zero-match selector gives NO_READY_ENDPOINTS with selectedCount 0; unready selected Pods give that reason with counts explaining the difference.
5. Choose the ready backend with lexically smallest Pod UID, a documented deterministic simplification. Record all eligible UIDs and the chosen UID. Do not retry another backend if the chosen one refuses the connection. Require its captured AppSpec.listeningPort to equal the resolved backend port. Metadata containerPort and Docker EXPOSE do not open a listener.
6. Invoke existing captured info()/simulateAssistant behavior only after reaching the listener. Preserve plan B's embedding, postgres-query and answer operations, fixture credentials and prepared responses. Add a safe diagnostic stage for an unknown configured PostgreSQL hostname: application status 503, code POSTGRES_CONNECTION, dependency failure reason DNS_NOT_FOUND. This is a fixture result, not a real DNS query. The normal .example hosts remain predefined fixtures outside AKS.
7. Add one correlated application log only if a handler was reached: requestId, Pod UID/name/namespace, method/path, status, image artifact ID and redacted dependency summary. A pre-handler routing failure produces a client trace without a fictitious app log. Keep startup messages intact when extending kubectl logs.

Do not change the three-operation dependency trace contract from plan B. Extra transport diagnostics belong inside operation diagnostics or route; successful traces still record embedding -> postgres-query -> answer. There are no new SQL/client-authoring requirements in this batch.
