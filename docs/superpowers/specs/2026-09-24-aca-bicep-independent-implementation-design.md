# Independent Bicep Lab implementation design

**Status:** Lab 15 implemented in the isolated worktree; scoped review and delivery are pending. The agreed journey and technical design remain the learning authority. Labs 13–14 are delivered and supply bounded modular Bicep, trusted deployment provenance, and runtime request/CPU experiments.

## Brief and starting state

`aca-bicep-independent` is journey order 15, content version 1, independent mode. A working first environment is supplied as an already deployed Bicep stack in `rg-aca-bicep-primary`; no verification is earned for the learner. A second resource group, Basic registry and healthy published image are also supplied, but its application stack is not. The learner receives one shared, parameterized five-module project, a complete `infra/first.bicepparam`, and an incomplete `infra/second.bicepparam`. The brief requires a second target with distinct registry, identity, environment, Foundry account/project/deployment name, app name, `APP_ENV`, replica bounds and image tag. The supported model **deployment name** differs; the pinned model profile remains `gpt-5-mini/2025-08-07/GlobalStandard` because that is the simulator's documented subset. Each target has its own published image whose captured Foundry endpoint/deployment matches that target. Seed setup builds the first artifact from first-target appsettings and a separate second artifact from temporarily substituted second-target appsettings, then restores the learner's initial shared project files; only sandbox/artifact/active-runtime results are copied. Both published tags and source snapshots are fixed and learner ACR builds remain disabled. Deployment never builds or publishes an image.

The module source has parameters for `APP_ENV`, min/max replicas and all resource names. Learners may edit supported module structures, provided both target graphs satisfy the contract. The second parameter file and group are explicit; no cross-group `existing` resource reference is allowed. The first stack remains visible and active while the second is authored. The task requires reapplying the current shared source to **both** targets, so an edit that makes the first environment nonreproducible fails even if its old active app still responds.

## Parameter selection and provenance

The CLI accepts only manifest-listed local `infra/first.bicepparam` and `infra/second.bicepparam` for this Lab, paired to their declared resource-group/deployment targets; Labs 13–14 keep their single accepted file. `infra/main.bicep` stays the only template. The parser/compiler take an explicit selected parameter path and parse the shared `.bicep` source plus that file; a draft or invalid *unselected* parameter file cannot affect the other target. Path traversal, remote parameters, inline values, arbitrary files and mismatched target/file pairings are rejected.

Source hash includes the shared `.bicep` files only. Parameter hash includes only the selected saved `.bicepparam`. File-version provenance includes shared source plus selected parameter file, so editing second parameters does not stale the first target, while editing a shared module stales both. Record a bounded `parameterPath` in previews, attempts, current summaries and command observations, and validate it against the Lab target map in `validateBehavioralRun` on hydration and after actions. Existing Lab 13–14 records without this field remain compatible and have first-file meaning; **Lab 15 rejects** missing, mismatched or tampered fields in retained previews/attempts/observations/current summaries before any default/backfill migration can reinterpret them. The Lab13/14 compatibility path remains valid. Trusted action effects recompile from the selected saved file, validate target/file pairing, and compare exact source/parameter/version tuples; they never accept caller-supplied graph or preview outcomes. What-if stays read-only and incremental create retains omitted resources.

`az deployment group show` is keyed by group and name; app-show observations identify the matching Lab target from group/app name and inherit its attempt's selected parameter file. The review panel offers an accessible target selector and displays the selected target's saved parameter file, preview/currentness, deployment/outputs, and local-simulation notice. Source edit/draft status remains shared. The selector is session-local and resets to the first target on reload; it only changes what is inspected, while all mutations remain Cloud Shell commands.

## Seed and acceptance

The seed produces two explicit supplied Basic ACRs and published application artifacts. The first Bicep stack is applied from the initial current shared source and first parameters with a healthy active app. After seeding, retain the first Sandbox resources and active runtime but reset `runtime.bicep` to empty, and clear seed scrollback/history/evidence/observations/previews. Keep a controlled `nextSequence` greater than any retained artifact sequence. Thus the first seed deployment is inspectable as live resources but cannot count as learner deployment or verification provenance. The second target begins without identity/environment/account/project/deployment/app or Bicep attempt. Both image artifacts are immutable to learner builds; `acrBuild` is available only to seed setup.

The first app uses the first Foundry deployment and a frozen baseline of image/artifact, `APP_ENV`, identity/registry, endpoint/deployment and scale policy. The second uses a distinct supported deployment name, `APP_ENV=staging`, and different min/max bounds. For **each target graph and assessment**, require a same-target existing ACR, app UAMI, environment, AIServices account, child project with correct parent, child model deployment with correct parent, app module-output endpoint/deployment links, and AcrPull/account role scopes/principal. Reject foreign-group references and cross-target aliases. The scenario runner proves a correlated HTTP 200 and a bounded CPU load at each target. Each request and CPU evidence record snapshots that target's current successful Bicep tuple (target group, deployment name, selected parameter file, source/parameter hashes and file versions), active app generation/artifact, and relevant scale policy; target-specific selectors and generations prevent cross-app reuse or unrelated-parameter staleness.

Assessment requires a current second-target preview, successful create, exact second graph/runtime and second request/load evidence. Then it requires a current first-target what-if and successful **no-change** create from the current shared files and first parameters, with first request/load evidence collected **after** the second target's proof and the first reapply. Trusted Lab15 what-if/create effects atomically reserve the current run `nextSequence` for **every** recorded preview and attempt, including failed and successful no-change creates, and increment it once; validate/show observations do not reserve a causal sequence. Experiment recording already allocates from the same counter. Validate each recorded sequence is unique across preview/attempt/evidence, strictly below `nextSequence`, and persistent on reload. Compare: second preview < second create < both second request/load < first preview < first create < both first request/load. Request/load order within one target is flexible. The first effective app image, account/deployment, settings and scale policy must equal its frozen baseline. Cross-target resource aliasing, a wrong parameter file, a CLI-only repair, syntax-only success, stale preview, or a healthy old first app with broken current Bicep source cannot complete.

Tasks give outcomes and measurable criteria rather than a command walkthrough. Hints and Solutions may reveal a supported sequence but do not execute it. A later shared source/target change invalidates affected verification; a semantic no-op reapply preserves unaffected runtime evidence. Preserve reload, assistance, Result and Restart. Both environments remain after topic completion; cleanup belongs to the Capstone.
