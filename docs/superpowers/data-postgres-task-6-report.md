## Implementation and Task 7 interface

`runDataFunction({ appSpec, sandbox, dataTarget, functionName, args, nowMs, ...existingCosmosOptions })` accepts `dataTarget = lab.dataTarget`, with `{ kind: 'postgres', resourceGroup, server, database, port }`. PostgreSQL calls fail closed without this target. Cosmos account/database options and fixture embeddings remain on their existing branch; PostgreSQL call charge defaults to zero, preserving numeric `totalCharge`.

`parseDataApp(files, manifest)` captures PostgreSQL client initialization in `appSpec.data.postgres = { globals, clientOps }`. `globals.DSN` is a literal expression. A module-level pool is a `call-sdk` expression with `call: 'postgres.pool.ConnectionPool'`, `receiverType: 'pg-pool'`, `lifetime: 'module'`, and bound expressions under `args` (`conninfo`, `min_size`, `max_size`, `open`, optional `kwargs`). Constant DSN arguments become literal strings. `clientOps` contains ordered assignment ops for non-scalar client bindings; runtime initializes fresh descriptors for each request, modeling module pool lifetime without persisting request sessions. Function-local pool expressions have `lifetime: 'request'`. Task 7 can inspect these serialized expressions and the actual request `calls`/`connections` to distinguish deployed pool mode; a local pool is deliberately reported as a new connection, not successful persistent pooling.

Recognized canonical call spellings: `psycopg.connect` or imported `connect`; `ConnectionPool` or `psycopg_pool.ConnectionPool`; `register_vector` or `pgvector.psycopg.register_vector`; `Jsonb` or `psycopg.types.json.Jsonb`. `dict_row` is recognized as a fixed row-factory symbol. General Python import alias resolution is outside this bounded subset: author templates using canonical names. Import statements themselves are scaffold declarations, not executed modules. `clients.py` helper functions are found and queued transitively, so `def connect(): return psycopg.connect(DSN, row_factory=dict_row)` is supported across files. A helper used directly as a context-manager call needs a direct recognized constructor return for receiver-type inference; arbitrary higher-order factory patterns fail closed.

Catalog lookup maps `pg-module`, `pg-pool`, `pg-connection`, `pg-cursor` to `postgres.module`, `.pool`, `.connection`, `.cursor`. Receiver types propagate through assignments, helper constructor returns, `with` bindings and chained `conn.execute(...).fetchall()`. Connection/cursor close methods are also recognized. Supported connect keywords include `autocommit` and `row_factory`; pool keyword options include min/max/open and `kwargs={"row_factory": dict_row}`. This teaching runtime models resource acquisition, SQL calls and row adaptation; it does not emulate asynchronous pool startup, waiting queues or transaction commit/rollback.

Each connection checks admission through the shared engine, using an empty-SQL read-only probe and consuming only its connection error. Libpq field-string DSNs support quoted values and backslash escapes. DSN host/dbname/port override target defaults; DSN port 6432 requires the engine's enabled PgBouncer admission. URI DSNs are unsupported. Every request owns its connection session; successive executes reuse `session.settings`, and a reused pool descriptor retains session settings only within that request. `with` closes resources in `finally`, including returns and SQL errors. Results include `connections: { opened, closed, active, events: [{event:'open'|'close', connection, port}] }`. Pool close events represent lease release in this model.

SQL execute evidence is `calls: [{ call, sql, plan, latencyMs, recall, rows, connection: 'new'|'pooled'|'bouncer', charge:0, source, error? }]`. A direct or request-local-pool acquisition adds 25 ms to its first SQL record only; subsequent executes share the already-open connection. Module pools use `pooled`; port 6432 takes precedence as `bouncer`. SQL statements run only through `executePg`, preserving preceding mutations and structured errors. Tuples use ordered `rowValues`; dictionary rows use ordered columns to construct last-key-wins objects. EXPLAIN converts each `plan.text` line into one tuple/dict row. Fetch cursors maintain a read position. `Jsonb` wrappers are registered in a request-local WeakSet so learner dictionaries cannot spoof adaptation; their payload is passed to the shared atomic literal binder. Plain dictionaries used as SQL params produce the psycopg-style adaptation error instead of silently adapting JSON.

PostgreSQL parsing supports typed local assignments, tuple params, ordinary/escaped/triple string literals, simple f-strings (including Python-like list rendering for vector interpolation), bounded numeric row subscripts 0–1024, list append, string join and bounded row loops. Formatting conversions/specifiers and other unsupported constructs retain `DATA_UNSUPPORTED`. Fixed baseline routes are included from `manifest.runtimeFunctions: string[]` or `manifest.routes` values that are strings or `{ functionName }`/`{ function }`, and their local callees are queued transitively. This route extension is PostgreSQL-gated.

## Fixed training scaffold contract

Task 7 should supply an integrity-protected `training_runtime.py` declaring canonical `embed(question)` and `training_answer(question, context)`, imported into `app.py`. These names lower as fixed helpers; the supplied module is never executed. Learner `build_context(rows)` must return `{ "sources": [numeric chunk IDs], "passages": joined passage text }`, and answer should return `{ "answer": training_answer(question, context), "sources": context["sources"] }`.

With a PostgreSQL target, `embed` looks up the six authored corpus questions and returns independent eight-dimensional vectors. `appSpec.data.embeddingsDeployment = 'embeddings-v2'` pads to twelve dimensions. Unknown questions return zero vectors of the selected dimensionality, so authored SQL distance thresholds can return empty actual rows. Cosmos keeps its original knowledge fixture mapping. `training_answer` evaluates both arguments but grounds output in the top context source and requires the corresponding real corpus passage to occur in `context.passages`; it never chooses an answer blindly from the input question. A known top source uses its authored answer, otherwise it returns the source passage. Missing/unknown sources or absent grounding return exactly `I could not find a relevant passage in the supplied sources.` Future v3 fixtures need a deliberate small extension here; no speculative registry was added.

## SQL tokenizer integration ruling

The first real unsafe-interpolation run showed `What's retained?` reaching SQL tokenization, which returned `DATA_UNSUPPORTED` for `?` before discovering the dangling quote. The controller explicitly authorized a minimal `pg-sql.js` correction beyond the original three-file ownership: remember the first unsupported token, advance past it and finish lexical scanning; unterminated quotes/comments retain `SyntaxError` priority. Lexically valid unsupported punctuation still returns its original unsupported error. Size/token guards remain. The runtime only prefixes messages whose engine code already equals `SyntaxError` with `syntax error:`; it uses no quote-count or separate SQL interpretation heuristic. A temporary runtime normalization tried during development was removed under that ruling.
