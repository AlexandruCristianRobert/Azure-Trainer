# Verify Lab behavior through a bounded local simulation

The existing trainer checks resource configuration, which cannot demonstrate scaling, probe recovery, or a working API integration. Extend the local Sandbox with guided file editing, immutable simulated image builds and deployments, deterministic experiments, and recorded verification evidence. Keep the application a local browser-based trainer: it will neither execute arbitrary learner C# or Bicep nor deploy real Azure resources or call live models.

Learners configure and deploy through Cloud Shell, edit supported application/infrastructure files, and use visual Experiment Controls to send requests, apply load, and introduce faults. Resource Blades remain read-only. This extends the interaction scope of [ADR-0001](0001-simulated-az-cli-over-in-browser-sandbox.md) while retaining its decision to simulate Azure locally.

The agreed curriculum contains 16 independently restartable Labs: Guided, Troubleshooting, and Independent Labs for Application Factory/deployment, CPU autoscaling, probes, Foundry-backed REST APIs, and modular Bicep, followed by a resumable Capstone Lab. Use one C# / ASP.NET Core starter across the journey. Hints and Solutions remain available, with assistance recorded separately from completion.

**Considered options:** Additional configuration-only Labs would be cheaper but would not teach diagnosis and recovery. A full coding workspace or real Azure integration would provide greater fidelity but would require execution infrastructure, authentication, cost management, and much wider language/service coverage. A single shared project spanning every Lab would offer continuity but would make later practice depend on earlier mistakes. Bounded simulation with isolated starting points provides repeatable practice within the current app's deployment model.

**Consequences:**

- Validate a documented subset of real file syntax and commands. Unsupported constructs must be identified as unsupported, rather than misrepresented as invalid Azure or invalid source code. No arbitrary code evaluation or outbound network calls are permitted in the simulator.
- Editing source does not change a published image or running app. Builds capture source; deployments capture the selected image and configuration; experiments observe the deployed version.
- Behavioral Tasks require scenario evidence. Relevant changes invalidate affected verification; unrelated progress is retained. Verified stage milestones survive deliberate final cleanup, and completed Lab Results remain historical records.
- Simulation timing and generated model responses must be visible as teaching approximations. Avoid presenting simulated performance as an Azure capacity guarantee.
- Preserve existing Labs and saved progress through compatibility adapters and versioned run migration. The new curriculum does not replace the existing HTTP-scaling Lab.
- Deliver **one Lab at a time**. When a Lab needs shared building blocks, deliver the smallest prerequisite increment first, verify it, then finish that single Lab. Do not batch several Labs or build the entire future simulation platform upfront. Each completed Lab needs its own verification and review before the next begins.

The [agreed curriculum](../superpowers/specs/2026-09-22-containerapps-learning-journeys-design.md) defines learning outcomes. The [technical design](../superpowers/specs/2026-09-22-containerapps-learning-journeys-technical-design.md) defines the implementation boundaries and incremental delivery contract. This ADR records the decision; it does not authorize starting application implementation in this documentation task.

## Delivery status

The first three Container Apps deployment Labs are complete. Guided covers saved .NET 10 source, a private simulated image build, managed identity pull access, a captured deployment, and a `GET /api/info` verification. Troubleshooting supplies a deterministic failed deployment and requires diagnosing and repairing its image publication, pull access and ingress configuration before a successful request. Independent starts from the reusable project and empty Sandbox, requires a different API service, listener and runtime environment, and verifies the active deployment through a fresh request. CPU Guided supplies a healthy private API and requires an intended CPU policy plus measured baseline, scale-out, overload ceiling and scale-in evidence under explicit simulated time. CPU Troubleshooting supplies an active measured throughput incident and requires a bounded policy repair, full-service proof under unchanged demand, and quiet scale-in. CPU Independent accepts multiple CPU sizes and utilization targets that meet measured steady and burst throughput requirements, followed by quiet scale-in bound to both successful load proofs. Guided health probes is complete: saved endpoint behavior, captured HTTP probe configuration, and measured two-replica startup, readiness and liveness evidence. Probe Troubleshooting starts in a measured startup restart loop and requires startup allowance repair, process-only liveness during an optional dependency outage, and true hang recovery. Probe Independent accepts different valid probe timing policies for a 30-second API when full startup, readiness and liveness traces meet bounded outcomes in any order. Guided Foundry integration is complete: the seeded API uses a caller managed identity, resource-scoped inference access, a captured Responses deployment, and valid/invalid request evidence. Foundry Troubleshooting starts with an active wrong endpoint and deployment, then requires the exact caller grant, bounded retry policy, and request evidence for recovery, 503 exhaustion, 504 deadline, and healthy service. Foundry Independent is complete: learners attach a dedicated inference identity alongside the registry-pull identity, implement and deploy the brief API, and prove valid, invalid, transient and persistent outcomes under a bounded retry budget. Guided Bicep is implemented with a supplied published image and Basic registry, bounded local modules, saved parameter and target provenance, request and CPU evidence, and unchanged reapply. Its deployment panel shows saved-file diagnostics and previews. Bicep Troubleshooting adds a durable wrong-target preview, a deployable decoy identity grant, and denied then recovered Foundry request evidence. Bicep Independent is implemented in this worktree, pending review and delivery. It requires staging deployment and request/CPU proof followed by a no-change primary reapply and fresh primary proof from shared Bicep source. The review panel selects target-specific provenance locally. The Capstone is implemented in this worktree, pending scoped review and guarded delivery. It uses seven ordered sealed stages, dual bootstrap/main Bicep roots, a deterministic live effective-config incident repaired from saved source, fresh post-incident evidence, an owned-resource cleanup checkpoint and a read-only Result. These are local simulated effects; no Azure resources or live model calls are made.

The probe model is a bounded teaching scaffold pinned to `Microsoft.App/containerApps@2025-07-01` probe fields. It accepts JSON-form YAML and explicit HTTP probes, uses an explicit one-second clock, and restarts immediately without modeling backoff or grace periods. Saved source, published image and active deployment have separate lifecycles. The trainer follows [Kubernetes probe gating](https://kubernetes.io/docs/concepts/workloads/pods/probes/) and [ACA probe documentation](https://learn.microsoft.com/en-us/azure/container-apps/health-probes/) while recognizing that the general readiness narrative and [ACA-specific support evidence](https://azureossd.github.io/2023/08/23/Container-Apps-Troubleshooting-and-configuration-with-Health-Probes/) differ on restart language. This decision does not settle that live-platform ambiguity.
