# Bicep troubleshooting Lab implementation design

**Status:** Lab 14 implementation design. The agreed journey and technical design remain the learning authority. Lab 13 is delivered and supplies the bounded Bicep engine.

## Learning sequence

`aca-bicep-troubleshooting` is journey order 14, content version 1, troubleshooting mode. The learner receives a supplied Basic ACR and healthy published .NET/Foundry API image, but no application stack or Bicep deployment. Three faults live in saved, local Bicep files and first-environment parameters. They are exposed in order by validation, what-if, and a runtime request. Hints and Solutions describe repair actions; revealing them never executes them.

1. `main.bicep` refers to a misspelled environment module output. `az deployment group validate` reports a located missing-output diagnostic. The learner fixes the source and validates again. The task requires a trusted successful validate observation bound to the repaired source, parameters and target. The initial failed command remains visible in Cloud Shell; it is not a machine gate because failed validation is not durable run evidence.
2. The parameter file gives a valid but wrong `environmentName` (`env-bicep-test`). A read-only what-if proposes that unwanted managed environment. The learner corrects the parameter to `env-bicep-incident`, saves it, then runs another what-if. The task requires both the historical wrong-target preview and a current corrected preview. Neither preview creates resources. A single bounded `runtime.bicep.incidentPreview` milestone captures the first successful wrong-environment preview through the trusted reducer, with target/name/source/parameter/file versions and the offending operation. Its parameter hash and saved version must match the seeded wrong parameter file, proving the original incident was previewed before correction. It survives the ordinary 10-preview history limit and reload, is validated as run-local provenance, and cannot be supplied by a command caller.
3. The identity module declares the intended app UAMI and a decoy UAMI. The app and AcrPull use the intended identity; the account-scoped Cognitive Services User role mistakenly uses the decoy principal through a genuine module output. This is a structurally valid role assignment and deploys, but the named `access-denied` POST scenario from the app identity returns HTTP 502, `FOUNDRY_ACCESS_DENIED`, and zero upstream attempts. The learner inspects the deployed role and caller, reconnects the Foundry role input to the intended principal, validates/previews/redeploys the saved source, and runs a separate named `recovered` POST scenario for a correlated HTTP 200. Each scenario has its own task/evidence ID and version. A manual CLI grant alone never satisfies the authoring task.

## Engine policy and safety boundary

The Lab 13 strict provider contract remains the default: one declared UAMI and exact registry/Foundry grants tied to the app. Lab 14 opts into a narrow `bicepIdentityFault` capability. With that capability, provider validation permits exactly two declared UAMIs and exactly two declared role assignments: one registry AcrPull for the attached app identity and one account-scoped Cognitive Services User for either declared identity. The roles must have GUID names, pinned fields/API versions, exact declared scopes, output-bound principals, and no duplicate or extra intended grant. It does not accept an unlinked literal principal, remote module, arbitrary role, or wrong scope. The app still attaches only one UAMI. A policy argument derived only from the trusted Lab capability flows through `validateBicepProviders`, `previewBicepDeployment`, `applyBicepDeployment`, CLI validate/what-if/create, and action-effect recompilation/replay. The default is strict; a caller-supplied policy is never accepted.

Activation under this policy requires the published image, attached app UAMI, exact registry AcrPull, existing Foundry account/deployment, and linked environment outputs. It may activate without an effective Foundry grant. The existing deterministic request simulation checks the active caller against exact account permission and supplies the access-denied observation. No live Azure service is called. Lab 13 retains its preactivation Foundry grant check.

The permitted decoy role is not itself a successful repair. The final gate recompiles the current saved graph and proves its one account Cognitive Services User role is linked to the attached primary identity module output, at exact account scope. It also requires a matching successful Bicep deployment tuple (source hash, parameter hash, every Bicep file version and target), effective account grant, active deployment and current `recovered` request. A manual CLI Cognitive Services OpenAI User grant to the intended identity can make a request succeed but cannot satisfy this graph predicate. A subsequent source edit stales preview and authoring proof, including changed-away-back edits. Semantic no-op redeployment preserves unaffected runtime evidence. Incremental mode may retain the decoy identity and prior wrong grant; the corrected GUID-name assignment previews as create, not modify. Completion never claims omission deleted them.

## Fixture and assessment

Reuse the Lab 13 pinned resource APIs, local module grammar, first parameter filename and `az deployment group` command shape. Give Lab 14 its own manifest ID, group, registry, app, account, deployment name, artifact source and Bicep inspection target. The supplied image is seeded through a seed-only ACR-build capability; learner builds are disabled so the incident remains reproducible. The starter files contain all three faults. Solutions repair the output, parameter, then principal connection in that order, with validate/what-if/create/show and named request actions.

Assessment uses reducer-recorded validate/deployment-show/app-show command observations and Bicep provenance, not text matching alone. A role-list command is useful to inspect the miswire, but is not a machine gate because it has no durable observation effect. Require the bounded wrong-preview milestone before correction, the access-denied named request after the initial successful decoy deployment, and the fresh `recovered` request after corrected source deployment. Preserve and reload evidence, Result, assistance and Restart through the native Lab engine. Extend the read-only Bicep panel to display both the historical wrong preview and current corrected preview. A failed validate diagnostic is shown immediately in the panel/Cloud Shell and remains in Cloud Shell history after reload; it is not persisted as Bicep provenance. Preserve prior Labs' behavior and guard delivery against the Lab 14 baseline. Use generic Bicep Lab CLI help/error wording rather than “guided Lab.”
