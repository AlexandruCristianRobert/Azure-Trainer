## Extension contract

### Quantities, requests and desired replicas

CPU accepts positive integer millicores such as 250m, whole cores or decimal cores with at most three fractional places, plus explicit request zero. Normalize to integer millicores. Memory accepts integer bytes or decimal quantities with Ki/Mi/Gi or K/M/G suffixes yielding integral bytes. Reject nonfinite/negative, CPU precision smaller than 1m, unsupported suffixes and out-of-bounds values with clear diagnostics. Trainer bounds: CPU <=4000m, memory <=16Gi; CPU limits must be >0 and memory requests/limits >=1 byte. Valid-but-unmodeled notation such as fractional-millibyte memory gets an unsupported-quantity message rather than silent reinterpretation.

Resources may omit either requests/limits map or one resource dimension. If a limit exists without its request, default that effective request to the limit. Without either CPU field, effective CPU request is absent and contributes zero scheduling reservation but cannot support utilization-based HPA. An explicit zero CPU request also cannot be a utilization denominator. No LimitRange admission defaults are present. Request must not exceed its limit when both exist. Preserve authored versus effective values for inspection.

Replicas-only changes mutate the Deployment scale and owned ReplicaSet count, adding/removing the difference; preserve existing Pod UIDs, container snapshots, startup state and template hash. A new ReplicaSet is not created just because replicas changed. New Pods go through scheduler, image/config capture and startup/readiness. Scale-down deterministically selects the highest Pod UID, immediately removes it from traffic, honors the one-second fixture grace and releases node reservations only on deletion. Existing template changes retain the earlier synchronous replacement teaching behavior; rolling updates are the next topic.

Support `kubectl scale deployment/assistant --replicas N -n assistant`, N 1-6. It changes live scale, not the saved file, and does not create autoscaler proof. Reapplying a manifest with explicit replicas resets live scale, and a live HPA can adjust it again at its next sync. Explain this ownership conflict. In the Guided Solution, remove spec.replicas before adopting HPA. On first creation an omitted field defaults to 1; removing a previously apply-owned field resets to the default once; subsequent applies that omit it preserve scale updates. Store per-object applied-field ownership for replicas so no-op apply cannot reset HPA repeatedly. Test this subset of apply semantics explicitly; do not claim a complete Kubernetes field-manager implementation.

### CPU, memory and samples

At each whole second, distribute aggregate local-work arrival rate equally over ready, nonterminating assistant Pods. Other request paths retain their existing router behavior; this fluid distribution is a load-generation fixture for capacity accounting, not an alteration to individual Service routing. Each active container needs 10m baseline CPU, including during initialization. Workload CPU demand per eligible Pod is 10m + requestsPerSecond/readyCount * units; units are simulated milliseconds, so the result is millicores. AI-wait uses 1ms local CPU/request; downstream elapsed time is not added to CPU.

Apply each container's CPU limit to its demand. Within a node, allocate the remaining 1000m among demands using deterministic max-min fair sharing, bounded by each demand/limit; no container can consume the whole node just because its limit permits it. Requests decide placement, not a per-container consumption ceiling. Record demanded, delivered and throttled CPU separately. If node sharing is necessary, label it a simplified contention model rather than Linux CPU-share fidelity. For each accounting second, availableWork=assignedBacklog+newArrivals and demandCpuM=10+availableWork*units. Completed fluid work is min(availableWork, max(0,deliveredCpuM-10)/units); the remainder becomes backlog rather than discarded successful requests. Drain backlog before later arrivals using the same work cost. The earlier no-backlog demand formula is the special case assignedBacklog=0.

Memory demand is base 96Mi plus the source's scratch set during local-work load. It does not decrease just because replicas increase: this is a per-process working set. If modeled usage exceeds its finite limit, terminate that container immediately with reason OOMKilled/exitCode 137, record previous-container evidence and schedule the existing restart backoff. OOM is an abrupt exit, so do not delay it by the probe termination grace. Reuse same-Pod container identity/restart behavior from plan E. A continuous workload can cause repeated OOM after restart. Do not label CPU throttling as OOM or turn an unschedulable Pod into a started process.

Node-memory pressure/evictions are outside this subset. When finite demands would exceed the node's remaining 1024Mi while all containers are within their own limits, end the resource experiment with a visible UNSUPPORTED_NODE_MEMORY_PRESSURE diagnostic; do not invent an arbitrary victim or falsely claim successful processing. Final configurations must stay within this bound at all required replicas.

Metrics are sampled over complete 15-second windows and HPA syncs every 15 seconds, aligned to runtime.simTimeMs. A newly ready Pod needs a full window after becoming Ready; Pending, terminated, restarting or partially ready-window Pods have no usable CPU sample. `kubectl top` displays latest valid samples plus age/window, and `<unknown>` for absent data. Reads do not make metrics appear. Memory columns use the same completed window's peak footprint for this teaching projection, explicitly labeled in help. Retain at most 40 metric windows per Pod, pruning deleted Pods after receipts no longer need their IDs.

### HPA schema and algorithm

Support autoscaling/v2 HPA targeting apps/v1 Deployment in the HPA's namespace, one Resource cpu metric with Utilization averageUtilization integer 10-100, min/max 1-6, and optional behavior.scaleDown.stabilizationWindowSeconds. Reject multiple HPAs controlling one Deployment in the trainer, unsupported metric types/fields, status supplied in YAML and dangling cross-namespace target syntax. Applying an HPA before its target exists is valid; status then reports an unavailable scale target until it exists.

The controller calculates utilization from actual delivered CPU divided by effective CPU requests. For the uniform single-container Deployment template in these Labs, this is equivalent to average per-Pod utilization. Do not use limits as the denominator or include dependency wait milliseconds. A missing/nonpositive CPU request makes ScalingActive=false with a FailedGetResourceMetric-style explanation; valid top samples can still exist. No usable metrics means no CPU-based recommendation and no scale-down on a fabricated zero sample.

With all relevant Pods measured, rawDesired=ceil(currentReplicas * currentUtilization/targetUtilization). A fixed tolerance of 10% around ratio 1 suppresses changes. Set aside unready/missing-sample Pods before initial ratio calculation. For a scale-up proposal, account for those Pods as zero contribution when recomputing against all nonterminating replicas; for a scale-down proposal, account for missing samples as target utilization and conservatively hold if any currently unready Pod would make a downscale ambiguous in this bounded model. Do not proceed if recomputation reverses direction or lands inside tolerance. Explain that this readiness-window model is a simplified conservative subset; the real controller has additional initialization heuristics. Report observed average utilization separately from adjusted recommendation.

Clamp recommendations to min/max. Enforce min/max even while CPU metrics are temporarily unavailable, recording bound enforcement separately from metric-driven scaling. For downscale, store each valid clamped recommendation with timestamp and use the highest in the configured preceding stabilization window. For scale-up, no stabilization delay; limit one sync's increase to max(4,currentReplicas) additional Pods, never beyond maxReplicas. Scale-down may remove up to all excess replicas per 15-second sync once stabilized. These fixed policies match the chosen basic controller profile; arbitrary behavior policies are unsupported.

Read current live replicas; never count a Pending desired replica as ready capacity. Update HPA status currentReplicas, desiredReplicas, currentMetrics, lastScaleTime and conditions AbleToScale/ScalingActive/ScalingLimited with reasons matching the actual decision. Keep a separate trainer decision trace for missing-sample adjustment, stabilization and placement limits. Write the Deployment scale through the same replicas-only path as manual scaling, with cause hpa and an HPA UID/timestamp receipt. Pending additions do not trigger imaginary node scale-out.

Recommendation history belongs to the HPA UID and current policy generation. A changed HPA spec starts a new history; a no-op apply and mere Deployment replica changes do not. Deleting/recreating an HPA cannot reuse the old history or proof. On workload completion, retain the real history; do not reset it to force quick scale-in.
