### Actual Python logging source

Keep the existing integration function's complete body under the name answer_core. Add this wrapper and helper to editable app.py; all other info, settings, formatter and health functions remain present:

```python
import json
import logging
from training_diagnostics import current_request_id

logging.basicConfig(level=logging.INFO, format="%(message)s")
logger = logging.getLogger("assistant")

def log_event(event, status):
    logger.info(json.dumps({
        "event": event,
        "request_id": current_request_id(),
        "status": status,
    }))

def answer(question):
    log_event("request.started", None)
    result = answer_core(question)
    log_event("request.completed", result["status"])
    return result
```

This is ordinary Python logging to the process stream, with JSON message bodies. The server supplies a request scope before invoking answer, including for empty input; the fixed adapter uses contextvars in its readable reference source and resets its token in finally. Outside a request, current_request_id returns None. No real interpreter executes in the browser. The source compiler projects supported calls and bindings into the finite integration graph.

Accept direct dictionaries or this helper, different local names and normal quote/whitespace choices. Support only the shown basicConfig/getLogger/info/json.dumps forms, literal event strings <=64 characters, current_request_id(), None, and the actual returned HTTP status binding. Parse valid but misplaced/missing log calls faithfully; grade whether start precedes the reached operations and completion follows the actual result. Unsupported syntax receives a located trainer diagnostic. A literal status/request ID is supported as a learner mistake but cannot pass correlation. No environment dumps, arbitrary object serialization or exception-text logging is part of this source subset.

The supplied runtime produces safe dependency records from actual adapter attempts; learners do not hand-author fake embedding/query/answer logs. Preserve the distinction between learner application logs, server access/startup logs, dependency observations and Kubernetes events. A successful known question has all three operation stages; invalid input has none, empty retrieval has embedding/query only, and a failed stage prevents later stages.

## Correlation, storage and incident contracts

### One request identity, several evidence sources

Allocate a deterministic request ID from run.nextSequence at the common request-dispatch boundary before routing, and increment the counter once. All internal curl, external Verify and scenario probes use this boundary. The router never allocates a second ID. A request that never reaches a handler still has a client trace, but no application/dependency records or container binding. Unsupported command syntax fails before dispatch and allocates no request ID.

Extend the existing request outcome with requestId and nullable podUid/containerId/artifactId. Do not replace the existing status/body/route/dependencyTrace/integrationTrace fields. Add appLogRecords to simulateIntegration's pure result for diagnosticsVersion 1; append them only through the common request recorder. Every emitted record gets immutable provenance from execution, separately from learner-authored JSON fields:

```js
// A stored record; sourceFields cannot overwrite envelope identity.
const record = {
  id: 'log-42', requestId: 'request-40',
  clusterId: 'cluster-fixture', namespace: 'assistant',
  podUid: 'pod-12', containerId: 'container-13', artifactId: 'build-7',
  simTimeMs: 25000, requestElapsedMs: 120,
  origin: 'application',
  sourceFields: { event: 'request.completed', request_id: 'request-40', status: 200 }
};
```

simTimeMs is the shared request-start clock; requestElapsedMs distinguishes dependency work within that request. Use sequence IDs to disambiguate multiple records at the same clock value. Do not claim simulated durations are production measurements. Server startup records have requestId=null and are not evidence of an HTTP call.

`recordRequestOutcome(run, target, outcome) -> run` owns request/log append and redaction. Reuse runtime.kubernetes.requests (max 100) and the existing per-cluster application log projection; do not append a second generic application log in the old router path. Store max 100 log records per current container, max 100 for the immediately previous container while its Pod exists, and max 30 dependency-attempt records per retained request. Surface truncation counts. Diagnostics logs and previous-log pointers follow the existing container lifecycle owner rather than inventing another restart count.

On restart within the same Pod, the old container's retained stream becomes previous and the new stream becomes current. `logs --previous` with no previous container gives the existing clear unavailable result. On Pod deletion, remove its live log store; immutable incident snapshots can still show what was recorded, with an explicit historical label. Do not make kubectl logs resurrect a deleted Pod. Reading logs never changes time or fault state.

Preserve Secret provenance redaction before persistence, console formatting, UI rendering and receipt creation. Store endpoint host/deployment name, configuration key/reference and safe dependency error code; never persist passwords, authorization values, raw connection strings or stack traces. A test fixture may place a credential value inside a permitted string to prove redaction follows provenance and known secrets rather than a field-name blacklist alone. This is a storage invariant, not a new security Lab.
