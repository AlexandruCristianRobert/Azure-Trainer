# Container Apps journey Capstone implementation design

**Status:** Lab 16 implementation design. The approved journey and technical design remain the learning authority. This Lab combines the delivered image, CPU, probe, Foundry and Bicep engines in one ordered, persistent simulation.

## Scope and starting point

`aca-capstone` is journey order 16, content version 1, capstone mode. Start from an empty Sandbox and an editable .NET 10 project with bounded C# source, appsettings, Dockerfile, `infra/bootstrap.bicep`, `infra/main.bicep`, their local modules and distinct literal parameter files. No registry, image, identity, environment, account, app, role, deployment provenance or evidence is seeded. All resources are run-owned. The brief specifies one private API that answers `GET /api/info`, handles bounded local CPU work, exposes startup/readiness/liveness health responses, and calls one deterministic Foundry deployment through `POST /api/summarize`. The learner gets acceptance criteria and optional help, not a default command walkthrough. No real Azure calls, tokens, containers or model responses occur.

The first release uses one attached user-assigned identity with **two separate exact-scope grants**: AcrPull on the registry and Cognitive Services User on the AIServices account. Both grants bind the bootstrap identity's principal ID; the Lab 12 two-identity exception is forbidden here. Missing AcrPull blocks activation, while missing inference access blocks requests. Exact role/scope/principal triples enter deployment provenance and evidence dependencies. The app has one container, external ingress, pinned CPU/memory, one CPU scale rule and explicit HTTP startup/readiness/liveness probes. The probe and CPU engines run sequential deterministic experiments; their separate replica projections are not presented as one real scheduler.

## Bounded application and infrastructure

Add a Capstone manifest and exact, bounded C# parser profile that combines `GET /api/info`, the bounded local CPU route, `POST /api/summarize` through managed identity, and startup/readiness/liveness handlers in one `appSpec`. The unified schema retains `foundry` (endpoint/deployment settings, request contract, retry policy), `healthEndpoints` (three executable status expressions), `infoRoute`, and `cpuRoute` (bounded work/response). No parser branch may return before the other contracts are parsed. Reuse delivered route grammars and located diagnostics, rejecting comments/string markers, unsupported statements and malformed settings. Pin three total Foundry attempts, a 10-second overall deadline, 3-second per-attempt cap, honored Retry-After when the next attempt fits, deterministic 1s/2s fallback and disabled SDK retries. Both transient-success and persistent-429 traces expose attempts, delays, caller identity, deployment, correlation ID, public/upstream status and deadline outcome. Build snapshots and active runtime retain all four fields. A source save does not change a published image or active app. Dockerfile and appsettings retain the existing safe-file limits.

The bootstrap root creates a Basic ACR and UAMI in one resource group; `infra/bootstrap.bicepparam` uses `./bootstrap.bicep`. Its outputs include registry server and identity IDs. The application root uses those exact resources as local `existing` declarations, then creates the ACA environment, AIServices account/project/model deployment, two role assignments and app. `infra/main.bicepparam` uses `./main.bicep`. Both roots use manifest-listed local modules and share the same resource-group scope; no cross-deployment output import, remote module, deletion by omission, or unsupported Azure syntax is claimed. Extend the existing bounded parser/compiler/CLI with an explicit trusted template/parameter/target map and root-specific source closure/hash/version tuple. A broken draft or saved application root cannot poison a bootstrap deployment. Existing Labs 13–15 retain their root and provenance behavior.

Under a Capstone-only provider policy, bootstrap may create Basic ACR and UAMI, while main may resolve the exact existing registry/UAMI. Main permits three pinned HTTP probe types with the full explicit tuple defined below on its one container, in addition to the existing CPU rule and Foundry output links. Preview and apply use the same canonical projection. App activation requires a published matching image, correct registry grant, account-scope inference grant, linked endpoint/deployment, and valid probes. Apply preserves previous active state on failure; a no-op reapply preserves unaffected evidence. The project builds and publishes `api:v1` only after bootstrap; main cannot deploy an absent image. Diagnostics distinguish unsupported fields/syntax from runtime failures.

## Stages, incident and evidence

The two literal parameter contracts share manifest-approved group, registry and identity names. Main's `existing` declarations must resolve to the exact successful bootstrap-owned resource IDs and output/source hashes; no cross-deployment output import is simulated. Root-specific source closure is used identically by command preparation, effect replay, deployment observation and validation. The Capstone provider profile alone permits creating the bootstrap Basic ACR/UAMI and resolving them as existing in main.

The Capstone container requires exactly one HTTP probe of each `startup`, `readiness`, and `liveness` type. Each explicitly binds `httpGet.path` to its parsed handler, `httpGet.port` to ingress/listening port, plus bounded `initialDelaySeconds`, `periodSeconds`, `timeoutSeconds`, and `failureThreshold`; readiness explicitly has `successThreshold`, while the other two are 1. Duplicate/unsupported transport, omitted fields, route/port mismatch and invalid thresholds fail. Preview, canonical equivalence and active deployment include the entire probe tuple; changed probes produce app modify, unchanged probes a no-op.

Seals are derived from actual task evaluation and evidence records at one reducer transaction. A seal stores the stage ID, content version, sequence, canonical sorted unique task/evidence IDs with each evidence sequence at or before the seal, and source/artifact/deployment/incident tuples. Hydration validates each historical seal **as of its stored sequence and dependency snapshot**, then validates only live recovery criteria against current generations. It rejects foreign, duplicate, future or evidence already stale at seal time before evaluating current Tasks; later drift does not erase a valid milestone. Stage advance and checkpoint creation persist atomically. Ownership IDs are captured immutably on group creation, never inferred from the groups still present. A valid partially completed Capstone reload, malformed optional fields, and pre-Capstone Labs 1–15 are separate migration fixtures.

Incident injection writes a persisted **preview-visible live-app drift overlay** on the Sandbox app projection, with effective `FOUNDRY_DEPLOYMENT`, incident ID and effective-runtime generation. The underlying active deployment snapshot, its provenance, saved main Bicep and desired configuration remain immutable. Effective configuration and evidence dependencies read the overlay when present; what-if compares desired against effective live projection and reports app `modify`. Successful main reapply atomically creates a restored active snapshot, advances its generation and clears the overlay; failed apply leaves both underlying active snapshot and overlay unchanged. The inference simulator reads the effective value, so the named missing-deployment request makes zero upstream attempts.

Cleanup uses a Capstone reducer wrapper around group deletion: capture deleted registry/app IDs, remove their owned published tags while retaining immutable build artifacts, reconcile active runtime with deleted apps, and persist deletion evidence. Check every immutable attempt-created group including partial/extra groups. A checkpoint is invalidated by a changed dependency fingerprint or generation (source, build, deployment, config or operating-condition experiment); an identical read-only rerun does not invalidate it. The stage-6 `advance-stage` transaction creates the checkpoint and enters Cleanup atomically. Thereafter deletion, inspection, help, time updates and the final `advance-stage` after cleanup verification preserve it; an experiment that changes operating conditions reopens Recovery.

The checkpoint binds the successful main Bicep attempt identity. An unchanged `az deployment group create` after checkpoint creates a new attempt and reopens Recovery even when the active app generation stays the same. It does not stale unaffected request/probe/CPU evidence; the learner can immediately reseal Recovery after the no-change apply passes. Read-only `what-if` and `show` preserve the checkpoint. Operational evidence also binds the current saved application build inputs to the published artifact's frozen source snapshot, so editing executable source or settings after publication requires a new build and active deployment before fresh proof can pass.

The single Lab has seven ordered stages with explicit `advance-stage` actions. The active stage can advance only when all its Tasks pass; the reducer seals a bounded immutable summary of task/evidence IDs, source and deployment tuples and a monotonic sequence. Sealed historical Tasks (especially build publication and pre-incident healthy experiments) remain visible as achieved after later changes, while live recovery Tasks must be reverified. A stage cannot be skipped. Stage transitions and seals are validated on hydration, including evidence identity/order and Lab content version.

1. **Prepare:** save buildable combined C# source, settings, Dockerfile, bootstrap and main Bicep/parameter files. Compilation is against saved files. Solutions may show one supported version.
2. **Bootstrap and publish:** create the one run-owned resource group, validate/preview/create bootstrap, inspect its outputs, build and publish `api:v1`, inspect captured source version. This milestone records the actual image ID/digest/source hash; it does not assert that a future active app is still healthy.
3. **Deploy:** validate/preview/create main from current saved files, inspect outputs and exact registry/Foundry roles. The app activates only after dependencies and carries the published source, CPU scale and probes.
4. **Healthy baseline:** earn named HTTP 200 with correlated Foundry invocation, startup gating/readiness/liveness proof under a slow-start fixture, CPU sustained scale-out, bounded overload and quiet scale-in. Each scenario records active image/configuration, selected graph tuple, generations and deterministic trace. Seal this historical baseline before an incident can begin.
5. **Incident and repair:** a one-shot `inject-incident` trainer action is available only after stage 4 seals. It changes only the Lab-owned live app's effective `FOUNDRY_DEPLOYMENT` to `missing-deployment`, creates a new effective-runtime generation, records an incident ID and diagnostic log, and leaves saved Bicep/source correct. A named request must observe HTTP 502 `FOUNDRY_DEPLOYMENT_NOT_FOUND` with zero upstream attempts under that incident ID. The learner inspects drift, previews the app modification, reapplies current main Bicep to restore the configured deployment, then proves a bounded transient 429/Retry-After→200 scenario. The repaired deployment must be sourced from current saved files, not a manual CLI fix.
6. **Recovery and reproducibility:** after the repair, rerun the healthy Foundry request, slow-start/probe proof, CPU sustained/overload/quiet proof and a bounded failure scenario such as persistent 429→503. Reapply the unchanged current main Bicep and verify no unintended changes while proofs remain current. This live gate requires the exact app/grants/source/image and all post-incident evidence. Advancing seals a pre-cleanup `cleanupCheckpoint` with evidence IDs/fingerprints, source/deployment tuple, incident ID, owned group/resource IDs and sequence.
7. **Cleanup:** delete Lab-owned group/resources with the simulated CLI and verify group, apps/environments, identities, registry/publications, Foundry account/children, roles and active runtime are absent. Build artifacts and immutable proof/checkpoint remain for Result inspection. Premature deletion never earns the checkpoint. Saved source/build/deployment/configuration changes or an experiment changing operating conditions clear it and reopen recovery; an identical read-only rerun preserves it. Cleanup completion freezes one read-only Result; Restart creates a fresh attempt.

The incident is a labeled local simulator fault, never a live service disruption. `simulateFoundryRequest` reads the effective active deployment setting and distinguishes the injected missing deployment from a downstream 429 trace. The saved main source remains correct so what-if must show an app modify before repair. Stage 4 and stage 6 evidence are separate named/versioned scenarios; old baseline evidence cannot satisfy recovery. Experiment routing selects CPU or probes by declared fixture and active scenario kind when both capabilities are enabled; it cannot accept caller-provided outcomes.

## Persistence and cleanup integrity

Extend `run.stages` with bounded Capstone seals, active stage and checkpoint validation. The Lab starts from an empty Sandbox, so every created group is owned; group deletion uses the existing cross-group dependency guards and must not remove unrelated resources. At final cleanup, require no remaining Sandbox resource in any group created during the attempt, no published tag owned by a deleted registry, and no active app projection. Extra or partially created groups must also be removed. No resource cleanup command can invent a seal or evidence. Reload, storage failure/recovery, paused scenarios, assistance, completion, export and Restart preserve the correct stage/checkpoint state.
