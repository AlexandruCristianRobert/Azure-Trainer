# Guided Bicep implementation design

Status: Guided Bicep engine, fixture, catalog, and reducer assessment implemented; the focused preview/provenance UI and final delivery gate remain pending. The agreed [journey design](2026-09-22-containerapps-learning-journeys-design.md), [technical design](2026-09-22-containerapps-learning-journeys-technical-design.md), and [ADR-0002](../../adr/0002-behavioral-labs-with-bounded-local-simulation.md) remain authoritative. This increment delivers only Guided Bicep; Labs 14–16 remain separate increments.

## Learner outcome

The learner completes a modular resource-group Bicep project, selects the first environment's `.bicepparam` file, validates and previews it, deploys the supported resource graph, inspects outputs, and proves the API's Foundry request. They then change a behaviorally relevant replica bound in source, preview and deploy the update, measure the new scaling behavior, and redeploy unchanged files to verify no duplicate resources or unintended changes. A valid source file, preview, or successful deployment alone cannot complete the Lab. The existing image and private registry are explicit supplied prerequisites; this Lab does not build an image.

## Supported authoring contract

The project editor exposes `infra/main.bicep`, a finite set of local `infra/modules/*.bicep`, and `infra/first.bicepparam` alongside the existing .NET project. Only manifest-listed files can be edited. Bicep paths are normalized project-relative paths; absolute, traversal, remote, and registry module paths fail. The parser lexes comments, strings, identifiers, punctuation, numeric and Boolean literals, and the supported interpolation form before producing a typed syntax tree. It never evaluates learner text as JavaScript or executes Bicep. Diagnostics carry file, line, column, and a stable code, distinguishing malformed syntax from valid but unsupported constructs. Lab13 bounds Bicep input to 12 files, 32 KiB/file, 128 KiB total, 10,000 tokens/file and 30,000 total, expression depth 32, interpolation segments 32/string and 1,024 tokens/segment, module depth 4, and 32 graph nodes.

The bounded language supports parameter declarations/defaults and `@description`, `@allowed`, `@minValue`, `@maxValue`; variables; object/array literals; property access; string interpolation; resource declarations (`existing` where applicable); module declarations with explicit `params`; outputs; and `dependsOn`. Expressions can refer to parameters, variables, resource IDs/properties, and module outputs. `@allowed` and min/max decorators are enforced on resolved parameters at compile time; implicit string/number/Boolean coercion is rejected. Accepted function shapes are `resourceGroup().id|name|location`, `subscription().subscriptionId`, `resourceId('<supported resource type>', <name>[, <child name>])`, and `guid(<one to five scalar strings>)`; unsupported argument types/counts fail with locations. `guid` uses the documented Bicep UUID-v5 namespace and ordered, hyphen-joined arguments, checked against reference vectors. `uniqueString()` is recognized as valid Bicep but returns an explicit unsupported diagnostic in Lab 13: Microsoft documents its 13-character deterministic shape but not an algorithm that this local simulator can verify. No Lab 13 fixture depends on it; add it in a later increment only with a trustworthy compatibility oracle. See the [official Bicep string-function contract](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/bicep-functions-string#guid) and [uniqueString documentation](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/bicep-functions-string#uniquestring). Interpolation accepts scalar expression segments only. Object/array members must be finite JSON values; secure/unknown resource properties are unsupported. Unsupported valid constructs receive `UNSUPPORTED_BICEP`; malformed syntax receives a syntax diagnostic. Cycles, missing modules/outputs/parameters, wrong types, unsupported scopes/functions/resources, and unsupported path shapes fail before mutation. The first environment's parameter file uses `using './main.bicep'` and literal values only.

The typed graph has stable logical IDs, exact target resource group, resource type/API version/name/location/body, module/output dependencies, and source locations. Inferred references and supported explicit `dependsOn` form a DAG. The graph compiler validates declarations and provider shapes without mutating the Sandbox. It pins these simulated ARM contracts: `Microsoft.ContainerRegistry/registries@2025-11-01`, `Microsoft.ManagedIdentity/userAssignedIdentities@2024-11-30`, `Microsoft.App/managedEnvironments@2025-07-01`, `Microsoft.App/containerApps@2025-07-01`, `Microsoft.CognitiveServices/accounts`, `/projects`, and `/deployments` at `2025-06-01`, and `Microsoft.Authorization/roleAssignments@2022-04-01`. These versions identify a teaching subset, not claims that every field or region/model combination is live-available. [ACR](https://learn.microsoft.com/en-us/azure/templates/microsoft.containerregistry/2025-11-01/registries), [UAMI](https://learn.microsoft.com/en-us/azure/templates/microsoft.managedidentity/2024-11-30/userassignedidentities), [ACA environment](https://learn.microsoft.com/en-us/azure/templates/microsoft.app/2025-07-01/managedenvironments), [ACA app](https://learn.microsoft.com/en-us/azure/templates/microsoft.app/2025-07-01/containerapps), [Foundry account](https://learn.microsoft.com/en-us/azure/templates/microsoft.cognitiveservices/2025-06-01/accounts), [Foundry project](https://learn.microsoft.com/en-us/azure/templates/microsoft.cognitiveservices/2025-06-01/accounts/projects), [Foundry deployment](https://learn.microsoft.com/en-us/azure/templates/microsoft.cognitiveservices/2025-06-01/accounts/deployments), [role assignment](https://learn.microsoft.com/en-us/azure/templates/microsoft.authorization/roleassignments).

The field allowlist is intentionally narrow. The ACR is `existing` only and must resolve to the seeded Basic registry; declaring a new registry is unsupported in Lab 13. UAMI permits `name` and `location` only. The managed environment permits `name`, `location`, and `appLogsConfiguration.destination: 'none'`. The account requires `kind: 'AIServices'`, S0, `identity.type: 'SystemAssigned'`, `allowProjectManagement: true`, and the exact account custom subdomain; project requires account parent and name/location only; deployment requires account parent, the simulated gpt-5-mini/2025-08-07/OpenAI model and GlobalStandard capacity 10. The app requires one container with `name`, seeded published `image`, supported CPU/memory, `APP_ENV`, `AZURE_CLIENT_ID`, `FOUNDRY_ENDPOINT`, and `FOUNDRY_DEPLOYMENT` env values, `environmentId`, one attached UAMI, one registry entry using that identity and the existing ACR server, external ingress/target port, min/max replicas, and one supported CPU scale rule. No Dapr, secrets, revision traffic, multiple containers, registry credentials, or extra provider fields are modeled. Immutable names, locations, and parent links cannot be updated in place.

The Guided fixture creates **one UAMI** and grants it AcrPull at the seeded registry plus Cognitive Services User at the Foundry account; it is both the pull and inference caller. Roles precede app creation/activation, so the existing single-identity app operation can attach it atomically. The app's `AZURE_CLIENT_ID` must resolve from the identity module output, while `FOUNDRY_ENDPOINT` and `FOUNDRY_DEPLOYMENT` resolve from Foundry module outputs; the captured application artifact must contain the same endpoint and deployment. The latter two env values are explicit Bicep connectivity evidence and are checked against the active source configuration; they are not a second, unmodeled runtime configuration channel. The app image expression must resolve through the `existing` registry's server and match the seeded published tag/artifact. Literal values that happen to equal these outputs do not satisfy the module-connection Task.

Role declarations require a GUID `name`, exact ACR or Foundry account `scope`, `ServicePrincipal` type, UAMI principal ID, and a full supported role definition ID. The Guided source uses `guid(scope.id, identity.properties.principalId, roleDefinitionId)`; other accepted scalar-string forms follow the function rule above. A Bicep-created assignment stores the declared UUID as the Sandbox assignment ID, while semantic equality also keys on `(scope, principalId, roleDefinitionId)`. Reapplying the same name and triple is a no-op; a different name for an existing triple or the same name for a different triple is a conflict, never silently adopted. Existing CLI-created assignments keep their legacy IDs. The graph records the full ARM role resource ID separately from the Sandbox UUID.

## Preview, deployment, and provenance

The simulated CLI accepts exactly `az deployment group {validate|what-if|create|show} --name <deployment> --resource-group <existing target> --template-file infra/main.bicep --parameters infra/first.bicepparam` (the target and name arguments also accept documented `-g`/`-n` aliases). No inline parameters, remote templates, complete mode, other deployment scopes, or implicit target defaults are accepted. `show` needs only name and group and returns the latest record for that pair; a repeated `create` appends a new immutable attempt under that key. These commands read **saved** files. Validate and what-if are read-only; validation does not count as preview. What-if reports create/modify/no-change/ignored-existing for the supported graph. A preview records the source hash, parameter hash, all relevant saved file versions, target group, target deployment name, and proposed operations in run-local provenance. Editing away and back or changing target/parameters makes a required preview stale. Caller-supplied preview or outcome fields are never accepted. Native `runtime.bicep` stores bounded JSON-safe provenance with at most 20 detailed attempts, 10 previews and eight target keys; monotonic attempt IDs never repeat, and compact current-success/failure summaries survive pruning. Old runs without this optional field remain valid.

Create applies the graph in dependency order through narrow adapters around the same Sandbox operations as CLI resources and records deployment ID, source/parameter hashes, target, applied operations, outputs, and any partial failure. Before calling a create-only Foundry operation, the adapter compares canonical desired/current state; equal state is `no-change`, and unsupported updates fail explicitly. A declared resource is reapplied with its complete supported desired configuration; omitted resources stay in incremental mode. Existing declarations resolve but do not create. Role assignments are ordered before activating apps that need their grants. A genuinely unchanged redeployment keeps resource IDs and relevant runtime evidence stable. A failed deployment remains inspectable and never fabricates success. Manual CLI repairs do not establish current source provenance.

The same per-provider canonical projection drives what-if classification, apply decisions, provenance comparisons, and evidence dependencies. It normalizes ARM ID/name casing and modeled defaults, omits generated timestamps, output-only IDs, tags, and unrelated Sandbox fields, and includes the full supported desired configuration for a declared resource. Compile/schema/graph errors cause zero mutations. During apply, completed non-app resource steps may remain if a later step fails, and a failed record lists them. The app is the final apply step: its supported CPU, memory, replica bounds, and scale rule are captured in the active deployment and included in deployment equality. CPU simulation reads this active policy, not an unactivated mutable Sandbox app policy. App activation and earned evidence update only after a successful full graph; if app activation fails, its Sandbox app mutation is rolled back and the prior active snapshot remains. Successful semantic no-ops do not increment runtime or evidence generations. Existing CPU Labs must keep their measured behavior, with regression tests for this capture change.

App activation still requires the seeded published image, attached UAMI with exact-registry AcrPull and exact-account `Cognitive Services User`, the intended Foundry account/project/deployment, and the seeded valid saved application artifact. Resource identity links in Bicep use full ARM IDs. The first Lab seeds the registry, image, healthy source and artifact, but the graph must explicitly reference the `existing` registry and its published image. It creates the UAMI, managed environment, account/project/deployment, roles, and app. A model response is the existing deterministic Foundry fixture, never a live inference call.

## Lab evidence and limits

Task evidence binds the saved Bicep graph and parameter version, target group, preview generation, deployment provenance, current resource state, active app artifact, request trace, and measured CPU result. A file change away and back after proof, target change, or relevant resource mutation requires fresh preview/deploy/experiment as applicable. Draft-only edits and semantic no-op redeploys preserve unaffected runtime proof. Completion and Restart use the existing native Result lifecycle. The Lab's worked Solution is one supported path; parser and assessor accept other equivalent supported edits. Hints and Solutions remain optional and recorded as assistance.

The simulator does not compile arbitrary Bicep, perform real Azure what-if, call Azure, build images in a deployment, model Bicep registries/loops/conditions/subscription or tenant scope, or delete omitted resources. Unknown valid syntax and unsupported provider fields are reported as such. [Bicep modules](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/modules), [parameter files](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/parameter-files), [what-if](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/deploy-what-if), and [incremental deployment mode](https://learn.microsoft.com/en-us/azure/azure-resource-manager/templates/deployment-modes) inform the bounded behavior.
