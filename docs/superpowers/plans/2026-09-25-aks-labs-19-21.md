## Review Focus

1. A healthy old ReplicaSet can hide a broken new revision behind successful requests; completion must inspect every desired new Pod and its captured artifact. Tasks 2, 4 and 6 test this.
2. Undo restores a retained Pod template, not ConfigMap/Secret contents, source files or the old contents of a mutable image tag. Tasks 1, 3 and 6 test this.
3. Ready, Available and rollout completion differ; surge, rounding, termination grace and node reservations must remain observable. Tasks 1, 2 and 7 test this.
4. A progress deadline reports stalled progress without automatic rollback; reloads and different time increments cannot change the diagnosis. Tasks 2, 3 and 6 test this.
5. Historical recovery proof and current deployment proof have different lifetimes; a YAML-only fix, stale image or replayed receipt cannot satisfy final deployment verification. Tasks 4-7 test this.

## Extension contract

### Revision identity and validation

Enable this controller only with kubernetesRollouts; earlier Labs retain their planned replacement behavior. Lazily initialize a missing rollouts state only in an eligible saved run. Seed/migrate the current template as revision 1 without replacing its Pods. Template equality excludes generated pod-template-hash labels and controller bookkeeping, but includes learner annotations and the rollout-restart annotation. Deployment replicas, strategy and metadata outside the Pod template do not create revisions.

Add Deployment defaults: RollingUpdate; maxSurge/maxUnavailable both 25%; minReadySeconds 0; progressDeadlineSeconds 600; revisionHistoryLimit 10. Trainer bounds: minReadySeconds 0-60, deadline 1-600 and greater than minReadySeconds, history 0-10. Surge accepts integers 0-6 or quoted 0%-100%; unavailable accepts integers 0-6 or quoted 0%-100%, capped to desired replicas when calculating the budget. Reject a configured zero/zero pair. Resolve surge percentages with ceiling and unavailable with floor; if nonzero percentage inputs both resolve to zero, set effective unavailable to 1 so a small Deployment can progress. Reject malformed quantities and unsupported fields before that object's mutation.

Each cluster gains the following serializable state; names are module contracts, not learner-editable Kubernetes fields:

```js
rollouts: {
  version: 1,
  deployments: {}, // Deployment UID -> DeploymentRollout
  experiment: null,
  receipts: [] // max 40; bounded sample arrays below
}
// DeploymentRollout:
// { nextRevision, currentRevision, currentRsUid, observedGeneration,
//   revisions: [{ revision, rsUid, templateHash, template, imageRef }],
//   availableSinceByPod: {}, lastProgressAtMs,
//   progressSnapshot: { updated: 0, ready: 0, available: 0, oldActive: 0 },
//   conditions: [] }
```

ReplicaSet resources own their live desired replica counts and Pod owners. Revision records refer to retained ReplicaSets; do not keep a second mutable copy of their replica counts. New templates allocate a new monotonically increasing revision. Returning to a retained template reuses that ReplicaSet and promotes it to the next revision number, replacing its previous history entry. Undo therefore creates a new current revision; it does not move the revision counter backward. Scaling alone creates no revision. Retain only revisionHistoryLimit old zero-replica ReplicaSets after completion; never delete a ReplicaSet with active or terminating Pods. Keep current plus retained old sets; requesting a pruned revision gives a precise error without mutation.

For deterministic browser memory bounds allow at most 20 retained/nonempty ReplicaSets per Deployment. On a new distinct template beyond this bound, return a trainer-limit diagnostic before mutation; recovery to a retained template remains allowed. History limits cannot erase an active incident's small immutable receipt, but receipts are not restorable ReplicaSets.

### Rolling controller, time and status

`reconcileRollouts(run, clusterId, atMs, lab) -> {run, changed}` uses current desired D, effective surge S and unavailable U. Implement bounded deterministic controller passes:

1. Count all nonterminating Pods across owned ReplicaSets; Pending and unready Pods consume surge slots. Create up to min(D - currentRS nonterminating count, D + S - total nonterminating count) new Pods when positive. Resource scheduling can leave them Pending.
2. Old unavailable Pods can be removed first without reducing available count. Remove old available Pods only while total available stays at least D - U. Visit oldest ReplicaSet revision first, then highest Pod UID. Never remove a current-template Pod simply because its readiness has not completed.
3. Mark selected Pods terminating, withdraw them from Service endpoints immediately and release resources only after their configured grace. Terminating Pods are excluded from the surge count but remain in resource accounting. Actual resident Pods may temporarily exceed D + S.
4. Stop once no immediate structural transition is possible. Newly created Pods do not become healthy without the existing clock/probe machinery. Bound passes by the finite Pod/ReplicaSet limits and fail an internal invariant if no convergence occurs.

For a replica-only change outside an experiment, use the preceding topic's scale behavior when stable. During a rollout, accept an increase by filling current-template capacity and a decrease by reducing old sets first within the new availability budget, then excess current Pods. Test these documented choices as the trainer's policy; full upstream proportional scaling and concurrent HPA are not modeled. During an active release experiment, changing desired replicas cancels that experiment but still applies the command normally.

At each due timestamp, process configuration/fault changes, scheduled starts and completed terminations, existing resource accounting/OOM, probe outcomes, readiness transitions, availability timers, rollout reconciliation, scheduling, Service endpoint refresh and then stream observations. Reconcile newly created containers at that timestamp before advancing further; preserve startup-probe gating. The existing time scheduler must include minReadySeconds expiry, progress deadlines and stream ticks in its next-event calculation. Equal elapsed time using one advance or many yields identical state and observations.

A Pod becomes Available only after continuous Ready duration >= minReadySeconds; reset its timer on readiness loss, termination or container restart. Completion requires D nonterminating current-template Pods, all available, and no active or terminating old Pods. Report updated, ready, available, unavailable and terminating counts separately. An unrelated old Pod's good response cannot establish completion.

Record progress when a new template is observed, current-template replica count/ready/available count increases, or old nonterminating count decreases. Repeated reads, unchanged probes and successful old-version traffic do not reset the deadline. At elapsed deadline with no subsequent progress set Progressing=False/ProgressDeadlineExceeded, preserving the actual live Pods. After repair, actual progress can restore Progressing=True. Available=True means the minimum availability budget is met; it does not mean the new release is complete. Completion sets Progressing=True/NewReplicaSetAvailable and stops the deadline timer.

```js
export function resolveRolloutBudget(spec, replicas) {
  const resolve = (value, round) => typeof value === 'string'
    ? round(replicas * Number(value.slice(0, -1)) / 100) : value;
  const surge = resolve(spec.maxSurge, Math.ceil);
  let unavailable = Math.min(replicas, resolve(spec.maxUnavailable, Math.floor));
  if (surge === 0 && unavailable === 0) unavailable = 1;
  return { surge, unavailable };
}
```
