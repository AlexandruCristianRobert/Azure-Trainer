Target app.py for the training profile (the Guided starter has incorrect/incomplete supported expressions described in Task 5):

```python
import os
from pathlib import Path
from training_clients import (
    EmbeddingClient, AnswerClient, PgClient, RetryPolicy,
    RequestBudget, DependencyError, as_vector,
)

SERVICE_NAME = "knowledge-assistant"
SERVICE_VERSION = "2.0"
PORT = 8080
SQL = Path("retrieval.sql").read_text()

def info():
    return {
        "service": SERVICE_NAME,
        "version": SERVICE_VERSION,
        "environment": os.environ.get("APP_ENV", "development"),
    }

def settings():
    return {
        "environment": os.environ.get("APP_ENV", "development"),
        "ai_endpoint": os.environ.get("AI_ENDPOINT", ""),
        "embedding_deployment": os.environ.get("EMBEDDING_DEPLOYMENT", ""),
        "answer_deployment": os.environ.get("ANSWER_DEPLOYMENT", ""),
        "pg_host": os.environ.get("PGHOST", ""),
        "pg_database": os.environ.get("PGDATABASE", ""),
        "pg_user": os.environ.get("PGUSER", ""),
        "pg_password": os.environ.get("PGPASSWORD", ""),
        "collection": os.environ.get("COLLECTION", ""),
        "audience": os.environ.get("AUDIENCE", ""),
    }

def answer(question):
    question = question.strip()
    if not question:
        return {"status": 400, "body": {"error": "Question is required."}}
    cfg = settings()
    policy = RetryPolicy(
        max_attempts=3,
        retryable_codes=("THROTTLED", "UNAVAILABLE", "TIMEOUT"),
        base_delay_ms=100,
        max_delay_ms=200,
        attempt_timeout_ms=200,
    )
    budget = RequestBudget(total_ms=1000)
    embedding_client = EmbeddingClient(endpoint=cfg["ai_endpoint"], sdk_retries=0)
    database = PgClient(host=cfg["pg_host"], database=cfg["pg_database"],
                        user=cfg["pg_user"], password=cfg["pg_password"], sdk_retries=0)
    answer_client = AnswerClient(endpoint=cfg["ai_endpoint"], sdk_retries=0)
    try:
        vector = budget.invoke(
            embedding_client.embed, policy,
            question=question, deployment=cfg["embedding_deployment"],
        )
        rows = budget.invoke(
            database.execute, policy, sql=SQL,
            params={
                "collection": cfg["collection"],
                "audience": cfg["audience"],
                "published": True,
                "embedding": as_vector(vector),
                "max_distance": 0.2,
                "limit": 1,
            },
        )
        if not rows:
            return {"status": 200, "body": {
                "answer": "No matching documents.", "sources": [],
                "environment": cfg["environment"],
            }}
        context = [{"id": row["id"], "content": row["content"]} for row in rows]
        result = budget.invoke(
            answer_client.generate, policy, question=question, context=context,
            deployment=cfg["answer_deployment"],
        )
        return {"status": 200, "body": {
            "answer": result["answer"], "sources": [row["id"] for row in rows],
            "environment": cfg["environment"],
        }}
    except DependencyError as error:
        return {"status": error.http_status, "body": {
            "error": error.public_message, "code": error.code,
        }}
```

Target retrieval.sql is ordinary parameterized PostgreSQL syntax:

```sql
SELECT id, content
FROM documents
WHERE collection = %(collection)s
  AND audience = %(audience)s
  AND published = %(published)s
  AND (embedding <=> %(embedding)s::vector) <= %(max_distance)s
ORDER BY embedding <=> %(embedding)s::vector ASC, id ASC
LIMIT %(limit)s;
```

`as_vector` validates finite numbers and returns a textual vector such as `[1,0,0]`, bound as a value and explicitly cast to vector in SQL. It does not interpolate values into SQL. ## Compiler and runtime extension contract

### Bounded Python and SQL projection

Compile the actual syntax tree and data flow into a versioned integration graph. Never decide success by finding method names in comments, comparing the source against a solution string, or forcing correct fixture values. Existing info/settings parsing remains. Add local variables, assignments, fixed imports, string.strip(), `if not` guards, dictionaries/tuples, keyword arguments, the two bounded row comprehensions, try/except DependencyError, bound adapter method references and the explicit Path retrieval.sql read. Renaming local variables, comments, quote styles and equivalent whitespace must work. Support literal bindings and vector literals/slices in the taught call slots so valid-but-wrong learner code can build and fail observably; provenance then prevents it from satisfying an embedding-use Task.

Reject arbitrary function calls, mutation, recursion, dynamic imports, while loops, filesystem paths other than the declared query, nested comprehensions and unbounded expressions with located unsupported diagnostics. Do not add eval, a general Python interpreter or a SQL database. Each supported statement has an explicit finite projection; each comprehension iterates at most three retrieved rows. Unsupported Python is distinguished from syntactically invalid Python. Supported control flow such as a missing empty-input guard or a constant source list is modeled as authored and fails the relevant behavior/provenance checks.

SQL parser accepts exactly one SELECT from documents returning id/content, an optional WHERE conjunction of collection/audience/published equality predicates and a cosine-distance cutoff, ORDER BY cosine distance [ASC|DESC] then id [ASC|DESC], and LIMIT. Each RHS is a named bound parameter; support different valid parameter names and bind by name, not a fixed map position. Omitted filters, reversed ranking and incorrect bound values are supported mistakes. No joins, subqueries, OR, writes, multiple statements or dynamic identifiers. Tokenize strings/comments/quoted identifiers before recognizing grammar; never strip comments using a regex that corrupts quoted text. Accept ordinary SQL whitespace, case and comments. SQL strings assembled using Python interpolation/concatenation are outside the taught parameterized subset and produce a specific diagnostic.

AppSpec gains `integration:{version:1,graph,querySpec,adapterDigest}` only in the new manifest. Graph has shape `{version:1,nodes,roots,bindings}` and is a finite JSON AST using op kinds literal, binding, dictionary, tuple, strip, guard, invoke, vector-format, context-rows, source-ids, return and catch. References use compiler-assigned binding IDs. Every node carries source path/line/column and outputs a tagged value whose provenance identifies embedding result, query rows, row content, source IDs or literal. Graph roots represent answer() execution order; there are at most 256 nodes. Client constructors compile to typed binding descriptors holding endpoint/configuration expressions; policy/budget constructors compile to validated finite descriptors, not executable Python classes. Fixed import/call dispatch chooses only the three adapter operations and the request-budget object. Validate all references, op fields and graph bounds when loading artifacts. Public output serializers remove internal provenance tags.

### Deterministic retries, timing and error outcomes

RetryPolicy supports max_attempts 1-3 (including first attempt), attempt_timeout_ms 1-1000, base_delay_ms 0-500, max_delay_ms 0-1000 and an explicit subset of THROTTLED, UNAVAILABLE, TIMEOUT. RequestBudget total_ms is 1-5000; the Lab 11 brief requires total <=1000 and per-attempt <=200. The Guided working source supplies the final policy while explaining it; Lab 11 starts with max_attempts=1 and requires the learner's correction. Adapter sdk_retries must be 0; reject nonzero values as unsupported in this trainer and explain retry ownership.

Every invoke shares the same budget object for one incoming request. Before each attempt, remaining=total-elapsed; zero remaining fails DEADLINE_EXCEEDED without a call. Effective timeout is min(attempt_timeout_ms, remaining). An operation with latency exceeding that timeout consumes only the timeout and records TIMEOUT. On a retryable error with attempts left, proposed delay is max(min(base_delay_ms * 2^(attempt-1), max_delay_ms), retryAfterMs or 0). If delay >= remaining, fail DEADLINE_EXCEEDED without waiting or starting another attempt. Otherwise add delay and proceed. Permanent errors and exhausted attempt counts stop immediately. No stage, retry or wait may exceed the shared budget.

Use request-local simulated elapsed time only. Do not advance runtime.simTimeMs, ConfigMap projection, Pod lifecycle or other requests during a synchronous fixture request. The trace explicitly labels these numbers simulated dependency durations, not benchmarked Azure latencies. Evidence uses existing engine timestamps plus integrationTrace.elapsedMs; no wall-clock sleep. Snapshot the Pod/image/configuration once at request start.

Immutable scenario profiles restart their attempt scripts for EACH request. Users can repeat a scenario but cannot consume its first failure globally. Each profile supplies stage responses/latencies only, never an expected passing outcome:

| Profile ID | Script | Result with target policy |
| --- | --- | --- |
| healthy | embedding 40ms, PostgreSQL 30ms, answer 50ms | 200 in 120ms, one attempt each |
| embedding-throttle-once | embedding THROTTLED after 40ms with retryAfterMs 150, then success 40ms; other stages healthy | 200 in 310ms, embedding attempts 2, one 150ms wait |
| postgres-unavailable-once | embedding healthy; PostgreSQL UNAVAILABLE after 30ms, then success 30ms; answer healthy | 200 in 250ms, PostgreSQL attempts 2; embedding not repeated |
| answer-unavailable-always | first two stages healthy; answer UNAVAILABLE after 50ms on every attempt | 503 DEPENDENCY_UNAVAILABLE in 520ms, answer attempts 3 |
| embedding-timeout-always | embedding latency 500ms on every attempt | 504 DEPENDENCY_TIMEOUT in 900ms, embedding attempts 3, no retrieval/answer |
| retry-after-too-long | embedding THROTTLED after 40ms, retryAfterMs 1500 | 504 DEADLINE_EXCEEDED after 40ms, one attempt, no extra wait/call |

The exact final attempt semantics above follow the declared policy: exhausting attempts returns the last mapped dependency error; refusing another wait because the request cannot fit it returns DEADLINE_EXCEEDED. Unit tests additionally exercise budget exhaustion in PostgreSQL/answer after successful preceding operations. Adapter attempts do not reset the budget.

Permanent errors include unknown endpoint/deployment, authentication, unsupported fixture input, vector dimension mismatch, invalid bound parameter types and unsupported context. They are not in the allowed retryable set. Public mapping: INPUT_REQUIRED 400; fixture input/context limitations 422 with an explicit simulation label; AI_ENDPOINT/AI_DEPLOYMENT 502; POSTGRES_CONNECTION/POSTGRES_AUTH/VECTOR_DIMENSION/QUERY_PARAMETERS 503; exhausted THROTTLED or UNAVAILABLE -> 503 DEPENDENCY_UNAVAILABLE; exhausted TIMEOUT -> 504 DEPENDENCY_TIMEOUT; DEADLINE_EXCEEDED -> 504. Error messages are fixed safe strings, never raw exceptions, passwords, connection strings or full environment dumps.

Query limits are integers 1-3; vectors require three finite nonzero components for this cosine fixture. Cutoffs are finite in [0,2]. Compute cosine distance in JavaScript, clamp floating roundoff to [0,2], filter by <= cutoff, then sort by distance and id with declared directions; retain unrounded values for comparison. Store display-rounded distances separately. A missing named binding is an observable QUERY_PARAMETERS failure. No rows returns 200/No matching documents./sources [] through the learner's branch, with embedding and PostgreSQL operations but no answer operation. Wrong context content/IDs returns the explicit fixture limitation; never fabricate the expected answer.
