## Source checks and simulation boundaries

Startup probes protect initialization; readiness governs Service traffic; liveness can cause container restart. HTTP success uses status codes 200-399. The [Kubernetes probe concepts](https://kubernetes.io/docs/concepts/workloads/pods/probes/) and [configuration guide](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/) document those relationships. Named HTTP ports are supported; TCP/exec/gRPC, custom headers, HTTPS and redirect handling remain explicitly unsupported.

The distinction between Pod identity and restarted containers follows [Pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/). Readiness projection reuses the [EndpointSlice](https://kubernetes.io/docs/concepts/services-networking/endpoint-slices/) behavior introduced in Labs 7-9. This trainer chooses classic 10/20/40/80/160/300-second restart backoff, resetting after 600 seconds of continuous running; real clusters can configure different backoff behavior. All sources checked 2026-09-25.

Probe timings here are deterministic teaching semantics. Real kubelet scheduling, immediate readiness retries, propagation latency, graceful shutdown and load balancing vary. Display the simulated schedule and explain these limits; do not promise that periodSeconds multiplied by failureThreshold is an exact production restart deadline.

Target health functions for Labs 13-14:

```python
from training_health import initialized, accepting_requests, postgres_available, ai_available

def startup():
    return {
        "status": 200 if initialized() else 503,
        "body": {"check": "startup"},
    }

def ready():
    return {
        "status": 200 if initialized() and accepting_requests() else 503,
        "body": {"check": "readiness"},
    }

def live():
    return {"status": 200, "body": {"check": "liveness"}}
```

The server maps GET /health/startup, /health/ready and /health/live to these functions and serializes their status/body. Returning 200 from live() means the handler can respond; a simulated process hang prevents dispatch of every HTTP handler, including this one. It cannot be bypassed by a literal return value. Health endpoints do not call the model or perform a query. Missing routes return 404 and wrong ports fail before handler execution.

For Lab 15 the explicit product requirement is that PostgreSQL is essential to admission, while the AI answer service is optional for basic endpoints. Its readiness implementation adds the cached database signal:

def ready():

## Extension contract

### Probe schema and health AppSpec

Deployment container fields startupProbe/readinessProbe/livenessProbe each support exactly one httpGet with an absolute path and integer port 1-65535 or existing named-port syntax. Optional scheme may only be HTTP. Accept valid-but-wrong paths/ports and observe runtime failures; a missing named port is a failed probe, not a parser-corrected value. Reject unsupported fields explicitly. Add Pod-template terminationGracePeriodSeconds integers 1-30 (default 30) and restartPolicy omitted or Always; other restart policies are invalid for this Deployment subset.

Defaults: initialDelaySeconds 0, periodSeconds 10, timeoutSeconds 1, failureThreshold 3, successThreshold 1. Trainer bounds: initial delay 0-120, period 1-30, timeout 1-10, failure threshold 1-30, readiness success threshold 1-3. Startup/liveness successThreshold must be 1. Larger otherwise-valid Kubernetes values receive a trainer-limit diagnostic, not a claim that Kubernetes disallows them. No probe-level grace override, readiness gates or publishNotReadyAddresses support.

The Python health compiler accepts Boolean constants, the four fixed signal calls, and/or/not, parentheses and conditional status expressions returning bounded literal HTTP statuses and string-key bodies. Function names startup/ready/live are required by the fixed HTTP adapter, but local names, whitespace and quotes may vary. It projects `appSpec.health:{version:1,endpoints:[{path,statusExpression,body}],helperDigest}` using a finite Boolean expression tree; ordinary info/answer integration is still compiled by plan D. Do not identify a correct implementation by searching text. Constant readiness or dependency-coupled liveness remains supported source and must fail behavioral exercises when inappropriate.

Without startup, their initial delay is relative to container start. Following checks start on period boundaries relative to their previous start; if a timeout overlaps a due start, skip that overlapping check and choose the next boundary strictly after completion. No concurrent probes of the same type. A 200-399 result is success, 400+ or connection failure is immediate failure, and a hung process completes a failed probe only after timeoutSeconds.

Initialization is true at now>=initializedAtMs. Schedule newly enabled readiness/liveness at the same timestamp when initialDelay=0. Keep seconds integer 1-300, max 10,000 scheduled events per advance; exceeding the bound rejects the whole candidate action with a simulation-limit diagnostic.

Changing probe YAML replaces Pods through normal Deployment reconciliation; a no-op apply does not reset timers. ### Readiness and container restarts

Readiness failure counts consecutive failures and removes traffic eligibility at failureThreshold; successful recovery requires successThreshold consecutive successes. It does not stop the process or reset its startup time. Project containerStatuses[].ready/started/restartCount/state/lastState and Pod Ready/ContainersReady conditions from health state. Keep phase Running when the Pod still has its running process even if Ready=false. EndpointSlices retain that Pod as ready=false rather than deleting the Deployment.

Startup/liveness threshold failure initiates container termination, cancels all pending checks for that container ID, marks it unready immediately and creates a typed probe-restart receipt. In this fixture the process exits at failureTime+terminationGracePeriodSeconds; show it as terminating during the interval. At exit, retain its latest logs/reason in previous, then wait 10*2^consecutiveRestarts seconds capped at 300 before starting the next container. The first delay is 10 seconds. Reset the backoff counter after 600 continuous running seconds; this is independent of readiness. While waiting, expose Waiting/CrashLoopBackOff with the computed next-start time as the trainer's chosen schedule.

The replacement container has a new containerId and incremented restartCount but the same Pod UID/name/IP, owner ReplicaSet and Pod-template hash. Re-run imagePullPolicy Always resolution and existing kubelet access validation, and resolve current environment/configuration for the new container. A missing image or revoked pull grant can leave it waiting; do not fake restart success. Cancel stale mounted projection entries and recreate them from the new snapshot. Preserve Pod volumes through the modeled lifetime, with ConfigMap/Secret content resolved under the existing projection rules. A restart clears only the terminated process's hang; a scheduled dependency outage or Pod admission fault stays active until its declared expiry.

Manual `kubectl rollout restart` creates new Pod UIDs through a template update; deleting a managed Pod also creates a new Pod. Neither action counts as liveness recovery. Record receipts with cause, old/new container IDs and Pod UIDs to distinguish all three operations. Successful automatic restart requires the original Pod identity and a probe failure cause; a learner cannot satisfy recovery just by deleting the hung Pod.

Add `kubectl logs POD -n NS --previous` to return only the most recent terminated container's log stream. No prior container yields an explicit diagnostic; it must not return another Pod's logs or the current stream. Probe failures normally appear in describe/events; a timed-out health handler has no fabricated successful application log. Keep current logs and all trace excerpts redacted by existing Secret provenance rules.

### Evidence and persistence

Experiment completion calls recordVerification for its one Task/scenario. Evidence stores the captured desired configuration/source fingerprint, original and final Pod/container identities, readiness intervals, actual automatic restart receipts, eligible backends and sampled request outcomes. Bounded summary counters/timestamps retain the proof even if the UI's ring buffer rolls over; do not infer success from a truncated last event. Use max 1000 recent health events per cluster, 100 samples per active experiment and 40 receipts; source/graph validator limits remain unchanged.

Experiment evidence is historical with respect to expected Pod/container turnover in later experiments, but current with respect to relevant saved/build/applied fingerprints and the stable Deployment UID. Compute the fingerprint from saved buildFiles, artifact ID, canonical Deployment/config/Secret/Service desired fields, and fixture version; exclude generated metadata/resourceVersions, current clock, status, Pod UIDs, health logs, and the server-managed kubectl.kubernetes.io/restartedAt annotation. Capture it after the experiment's internal rollout operation. Internal experiment restarts therefore do not bump these configuration dependency generations. This lets a cold-start experiment and later hang experiment both remain satisfied. A changed-and-restored user configuration still invalidates its generation counters. Each Lab also requires a final ordinary aks-request through the Service from the current running image and both Pods Ready; running a new experiment invalidates that live final proof, which is rerun last.

Lab 14's initial diagnosis Tasks are historical across intended repairs: they retain the observed bad source/probe fingerprint but depend on stable Deployment UID and immutable fixture version, not the repaired source hash. Their predicate checks the owned diagnosis receipt, never the obsolete bad current configuration. Its final healthy startup/dependency/hang proofs depend on the repaired current fingerprint. No ACA capstone stage sealing or manual done flags.

Persist active experiment, pending timeout deadlines, clock, counter streaks, previous-container logs, backoff and fault expiry. Reload must resume rather than reset them. Validate current container IDs and snapshots, deadlines, probe type thresholds, bounded counters, active scenario membership and receipt ownership. Older Labs legitimately omit health; malformed probe-enabled saves use the existing export/restart recovery path without silent reseeding.
